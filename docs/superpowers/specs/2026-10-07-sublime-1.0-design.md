# Sublime 1.0 — design specification

**Status:** Approved in conversation on 2026-10-07; awaiting review of this written specification  
**Repository:** `D-Synx/Sublime`  
**Target:** A first stable release of a small, expressive PHP HTML builder

## 1. Intent

Sublime should make ordinary HTML composition feel direct in PHP: a small number of obvious conventions should cover simple pages, conditional output, reusable components, and larger nested structures. The API should remain readable when the tree grows, and the library should behave predictably for the PHP values commonly used to build that tree.

Version 1.0 will turn the existing prototype into a documented, tested, installable library. It will preserve the core functional and immutable approach while correcting packaging, correctness, and security gaps. It will not attempt to become a full-stack framework.

## 2. Goals

- Make the first example understandable within a few lines.
- Keep the underscore tag helpers and the `Sublime()` entry point as the simplest path.
- Keep `TagFactory` for callers who prefer dynamic methods or want fewer imports.
- Define supported child and attribute values instead of relying on incidental PHP casts.
- Escape ordinary text and attributes by default; make unescaped HTML explicit.
- Ensure the documented Composer installation actually loads both classes and helper functions.
- Make the test suite and CI exercise the public contract across supported PHP versions.
- Present limitations honestly, especially around raw HTML and untrusted CSS.

## 3. Non-goals for 1.0

- Client-side hydration, JavaScript event binding, or a browser runtime.
- A template language, template inheritance, routing, or application framework.
- Automatic component discovery or dependency injection beyond the existing optional `TagFactory`.
- A general-purpose HTML sanitizer. `raw_html()` remains an explicit trusted-markup escape hatch.
- HTML parsing, DOM mutation, or automatic correction of invalid document structure.

## 4. Supported runtime and package

- Require PHP `>=8.3`, aligning the first stable release with maintained PHP branches at the time of this decision.
- Keep runtime dependencies at zero.
- Keep PHPUnit, PHPStan, and PHP CS Fixer as development tools.
- Use Composer PSR-4 autoloading for classes and Composer's file autoloading for namespaced helper functions; prove this with a consumer-style test that starts from `vendor/autoload.php`.
- Use Git tags for release versions rather than a hard-coded Composer `version` field.
- Keep releases on a reviewable branch until tests and CI pass; do not publish to Packagist as part of this work.

## 5. Public API and value contract

### 5.1 Composition

Keep the existing patterns:

- `div_('text')`, `div_(data: [...])`, and positional children.
- `Sublime(fn () => ...)` for rendering a tree.
- `TagFactory` injection for `$tags->div(...)`, custom tags, fragments, and raw markup.
- Immutable `withChildren()` and `withAttributes()` methods.
- `document()`, `fragment()`, `render()`, and `stream()` where they have consistent behavior.

A function declaration named `sublime()` must not be maintained separately from `Sublime()`: PHP function names are case-insensitive. The canonical documented spelling will be `Sublime()`; a distinct legacy alias such as `sublime_()` may remain only if it is tested and documented.

### 5.2 Child values

Normalize child values recursively and in input order:

| Value | V1.0 behavior |
|---|---|
| `HtmlElement` | Render as a nested element |
| `RawHtml` | Emit its contents without escaping |
| `string`, `int`, `float` | Convert to text and HTML-escape |
| `Stringable` | Convert once to text and HTML-escape |
| `null`, `false` | Omit |
| `true` | Render as `1` for compatibility with the current scalar conversion |
| Arrays and finite iterables | Recursively flatten; discard keys |
| Other objects, resources, closures, unsupported values | Throw a clear `InvalidArgumentException` |

Normalization must happen when the element is built so immutable elements do not retain a live iterator or defer arbitrary user code until rendering. Guard excessive nesting and report it as an input error rather than recursing indefinitely.

All text escaping must use UTF-8, quote escaping, and substitution for malformed byte sequences.

### 5.3 Attribute values

- Accept `string`, `int`, `float`, and `Stringable` values; escape them as attribute values.
- Omit `null` and `false`.
- Emit actual `true` values as a bare attribute only for recognized HTML boolean attributes.
- Render booleans on `aria-*` and `data-*` attributes as the literal strings `true` and `false`, preserving meaningful accessibility and data state.
- `class` accepts a string, a list of class-name strings, or an associative class-name-to-boolean map; empty names and false entries are omitted.\n- `style` accepts a string or an associative CSS-property-to-scalar map; null, false, and empty-string values are omitted. Validate property names and HTML-escape the final attribute, but do not claim to sanitize CSS values.
- Reject arrays and objects for other attributes with a clear error instead of PHP's incidental `Array to string conversion`.
- Validate tag and attribute names. Reject inline `on*` event-handler attributes.
- Validate dangerous URL schemes consistently across `href`, `src`, `action`, and `formaction`, including case and leading-control/whitespace variants. Add a regression test for each blocked scheme and attribute family.
- Reject children supplied to HTML void elements instead of silently dropping them.

Raw CSS values are not sanitized. The documentation must say that style values and `RawHtml` must not contain untrusted content.

### 5.4 Callback contract

`Sublime()` accepts a callback with no declared parameters or one declared parameter (typed as `TagFactory` or untyped) and supplies the factory for the latter. Reflection behavior must be predictable for closures, named functions, static methods, callable arrays, and invokable objects. Other signatures fail with a clear `InvalidArgumentException`. The callback result is normalized using the same child-value rules; unsupported result types therefore fail consistently.

## 6. Security and error behavior

- Escape text and attributes at their output context.
- Keep `RawHtml` opt-in and visibly documented as trusted content.
- Block inline event-handler attributes.
- Reject malformed tag/attribute names and unsafe URL schemes.
- Avoid silent data loss: invalid values and children of void elements produce descriptive exceptions.
- Do not claim that HTML escaping sanitizes URLs, CSS, or raw markup.

## 7. Test and CI requirements

The suite must test public behavior, not mirror private implementation. At minimum cover:

1. Simple rendering, nested components, positional and named child forms.
2. Every row in the child and attribute value contracts, with data providers for scalar and stringable cases.
3. Nested arrays/iterables, order preservation, false/null omission, true conversion, and nesting limit.
4. Text and attribute escaping, UTF-8 edge cases, raw markup, and fragment parity.
5. Boolean attributes plus `aria-*` and `data-*` booleans.
6. Class lists and style maps, including empty values and invalid shapes.
7. Tag/attribute validation, void elements, and URL scheme regressions.
8. Immutability, render caching, and equivalence of `stream()` and `render()`.
9. `document()`, `TagFactory`, all supported callback forms, invalid callback signatures, and unsupported return values.
10. Composer consumer autoloading and at least one complete README example.

CI must run coding standards, static analysis, and PHPUnit on PHP 8.3, 8.4, and 8.5. The default branch must be green before the 1.0 release is tagged. No claim of complete support should be made until the matrix passes.

## 8. Documentation and release presentation

Rewrite the README around the user's first successful render:

1. One-sentence value proposition and CI/license badges.
2. Install and a copy-paste quick start.
3. The two composition styles: helper functions and `TagFactory`.
4. Child/attribute type behavior and escaping rules.
5. Components, fragments, full documents, and streaming.
6. Security guidance for `raw_html()`, URLs, and CSS.
7. Supported PHP version, testing commands, examples, roadmap, and license.

Update examples so they run from the Composer autoloader and match the final API. Update the changelog with the 1.0.0 scope and any deliberate compatibility changes. Keep the documentation concise and avoid promising untested behavior.

## 9. Acceptance criteria

Sublime 1.0 is ready when:

- The Composer consumer example and all examples run.
- The behavior of every supported input category is documented and tested.
- Known invalid and dangerous inputs fail safely and predictably.
- The complete PHPUnit suite, PHPStan, coding-standard checks, and PHP 8.3–8.5 CI matrix pass.
- The README communicates the simple core idea without presenting the library as a framework.
- The 1.0 release remains unpublished until the user elects to publish it.

## 10. Implementation notes and known risks

- The current implementation is concentrated in `src/Sublime.php`; changes should preserve a small mental model and avoid broad refactoring unless needed to make the public contract testable.
- The current Composer configuration maps classes with PSR-4 but does not declare function-file autoloading.
- The current source declares `Sublime()` and `sublime()` separately despite PHP's case-insensitive function names.
- Local PHP and Composer executables are unavailable in the current workspace. Validate through GitHub Actions after pushing the implementation branch, and report any CI or environment limitation rather than inferring success.
